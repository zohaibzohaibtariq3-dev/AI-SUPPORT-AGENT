# TechNova AI Customer Support Agent

A small but complete AI customer support application. It answers policy
questions using retrieval-augmented generation (RAG) over a company
knowledge base, looks up real order status from a database, escalates to a
human when needed, and keeps a searchable chat history — all backed by a
real LLM (Groq) making real tool calls.

## What it actually does

- **Chats with Groq**: every reply is generated by a Groq-hosted LLM
  (`llama-3.3-70b-versatile` by default), not canned text.
- **Retrieves real knowledge**: policy questions are answered using chunks
  retrieved from `knowledge_base/faq.txt` via a FAISS similarity search over
  `sentence-transformers` embeddings. The model is instructed to only use
  this retrieved context for policy answers, not to invent one.
- **Calls a real tool for orders**: when a customer asks about an order, the
  model calls a `get_order_status` function which queries a SQLite table of
  sample orders and returns real data.
- **Escalates for real**: when a customer asks for a human, or the AI can't
  resolve the issue, the model calls `create_support_ticket`, which writes
  an actual row to a `tickets` table in SQLite.
- **Persists history**: every conversation and message is saved to SQLite
  and can be reopened from the sidebar.

## Prerequisites

- Python 3.10+
- Node.js 18+
- A free Groq API key: https://console.groq.com/keys

## Setup

### 1. Configure your API key

```bash
cp .env.example .env
```

Edit `.env` and paste your Groq key:

```
GROQ_API_KEY=gsk_your_key_here
```

(`.env` at the project root works — the backend searches upward from
`backend/` and will find it. You can also put a copy directly inside
`backend/` if you prefer.)

### 2. Backend

```bash
cd backend
python3 -m venv venv
source venv/bin/activate   # Windows: venv\Scripts\activate
pip install -r requirements.txt
uvicorn main:app --reload --port 8000
```

The first request will download the `all-MiniLM-L6-v2` embedding model
(~90 MB) and build the FAISS index; this is cached afterwards. Sample
orders and tables are created automatically on startup.

The API is now live at `http://localhost:8000` (interactive docs at
`http://localhost:8000/docs`).

### 3. Frontend

In a new terminal:

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`.

## Trying it out

Once both servers are running, try:

- **"Where is my order #1005?"** → the AI calls the order lookup tool and
  shows a live order status card (try `1001`–`1006`, or an invalid number).
- **"What's your refund policy?"** → the AI retrieves the Refund Policy
  section from the knowledge base and answers only from that content.
- **"Can I cancel my order after it's shipped?"** → answered from the
  Cancellation Policy chunk.
- **"I want to talk to a human"** → the AI creates a support ticket in
  SQLite and shows an escalation notice.

You can start a new chat, revisit past conversations from the sidebar, and
delete conversations you no longer need.

## Configuration

Environment variables (in `.env`):

| Variable       | Required | Default                    | Description                    |
|----------------|----------|------------------------------|----------------------------------|
| `GROQ_API_KEY` | Yes      | —                             | Your Groq API key                |
| `GROQ_MODEL`   | No       | `llama-3.3-70b-versatile`     | Groq model used for chat/tools   |

The frontend reads `VITE_API_BASE` (defaults to `http://localhost:8000/api`)
if you need to point it at a different backend URL — set it in a
`frontend/.env` file.

## Notes on how the agent works

1. On each user message, the backend embeds the message and searches the
   FAISS index for the most relevant policy chunks.
2. Those chunks are injected into the system context sent to Groq, along
   with recent conversation history and two tool definitions
   (`get_order_status`, `create_support_ticket`).
3. Groq decides whether it needs a tool. If it calls `get_order_status`,
   the backend queries SQLite for the real order and returns the result to
   the model, which then writes a natural-language reply.
4. If it calls `create_support_ticket`, a row is inserted into the
   `tickets` table and the customer is told their issue was escalated.
5. Both the user's message and the assistant's final reply are saved to the
   `messages` table so the conversation persists across reloads.

## Resetting the database

Delete `backend/support.db` and restart the backend — it will be recreated
and reseeded automatically.
